## Case Study

**Organisation / scenario:** Riverbend Teaching Hospital — a simulated 500-bed tertiary
teaching hospital operating outpatient, inpatient and laboratory services.

**Nature of the system:** A clinical records system supporting patient registration,
appointment scheduling, clinical encounters, prescriptions, admissions and laboratory
results.

**Users of the database:**

| User | Interaction |
|---|---|
| Receptionist | Registers patients, books/reschedules appointments |
| Triage nurse | Records vitals, updates appointment status |
| Doctor | Records encounters, diagnoses, prescriptions, lab orders |
| Lab technician | Records lab results against ordered tests |
| Pharmacist | Dispenses against active prescriptions |
| Ward clerk | Manages admissions, transfers and discharges |
| Records officer | Corrects records, handles merges |
| Administrator | Manages reference data |
| Auditor | Read-only access to the append-only audit log |

**Major data stored:** patients, next of kin, staff, doctors, departments, wards, beds,
appointments, encounters, admissions, vitals, diagnoses, prescriptions, laboratory tests
and results, and an append-only audit log.

**Key operations the database must support:**

1. Register a patient and issue a medical record number.
2. Book an appointment without double-booking a doctor, even under concurrent access.
3. Record an encounter — vitals, diagnosis and prescriptions — as one atomic unit.
4. Order a laboratory test and attach results with reference ranges and flags.
5. Retrieve a patient's full clinical history across all care settings.
6. Admit, transfer and discharge an inpatient.
7. Produce operational reports — doctor workload, lab turnaround, ward occupancy.
8. Audit all access to and changes of clinical records.

> Full description and design justification: [`docs/case-study.md`](docs/case-study.md)

## Running the Environment

Requires Docker Desktop.

```bash
docker compose up -d
```

To start only what you need — Portfolio 1 and 2 do not use MongoDB, and skipping its
~300 MB image is worthwhile on a slow connection:

```bash
docker compose up -d postgres
```

| Service | Port | Credentials | Needed from |
|---|---|---|---|
| PostgreSQL 16 | 5432 | `portfolio` / `portfolio` | Portfolio 1 |
| MongoDB 7 | 27017 | `portfolio` / `portfolio` | Portfolio 4 |

On first boot PostgreSQL executes `schema.sql` then `seed-data.sql` automatically.
To rebuild from scratch after changing either file:

```bash
docker compose down -v && docker compose up -d
```

### If the Image Pull Fails

A `short read ... unexpected EOF` during a pull is a dropped connection, not a bad
configuration. Docker discards the incomplete layer and needs to fetch it again.

```bash
docker compose pull          # shows per-layer progress, unlike up -d
docker compose up -d postgres
```

Completed layers are cached, so a retry re-downloads only the layer that failed.

If it fails repeatedly, reduce parallel connections and raise the retry count in
**Docker Desktop → Settings → Docker Engine**:

```json
{
  "max-concurrent-downloads": 2,
  "max-download-attempts": 10
}
```

Apply and restart. Fewer parallel streams is slower in theory but far more reliable on a
congested link. Also confirm there is room on disk — both images need about 2 GB once
unpacked.

Connect with `psql -h localhost -U portfolio -d hospital` or `mongosh`.

MongoDB is created and validated on first boot, but it is **not seeded with the 93,885
laboratory reports** by the init script. Load Portfolio 4 from the same PostgreSQL source
after the relational database is ready:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/load-p4.ps1
```

The loader exports PostgreSQL to NDJSON, stages it, converts the dates and `$merge`s the
documents into the validated collection. `scripts/capture-p4.ps1` regenerates the P4
evidence and `sample-documents.json`.

### Portfolio 5 Replication Cluster

Portfolio 5 uses its own primary and hot-standby replica, `portfolio-p5-primary` and
`portfolio-p5-replica`, on the private Docker network `portfolio-p5-repl`. It does not
reuse `portfolio-postgres`, and it publishes no host ports. The setup is destructive because
it reloads the full seed data into a clean P5 volume:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File `
  portfolio-5-distributed-cloud/replication-setup.ps1 up -Force

powershell -NoProfile -ExecutionPolicy Bypass -File `
  portfolio-5-distributed-cloud/replication-setup.ps1 status
```

`up -Force` removes the previous P5 containers, volumes and network, creates the primary,
loads `schema.sql` and `seed-data.sql`, takes a `pg_basebackup`, and starts the replica.
The other actions are `lag`, `sync`, `stale`, `configs`, `failover` and `down`. After
`failover`, the original primary is stopped and the promoted replica is the only writable
node; run `up -Force` to return to the two-node topology.

To regenerate the P5 evidence in one run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/capture-p5.ps1
```

That capture is also destructive and reloads the seed. Use `-SkipSetup` only when the
existing P5 cluster is healthy and you want to recapture the later steps.

### Confirming It Finished

`docker compose up -d` returns as soon as the containers start. PostgreSQL then runs
`schema.sql` and `seed-data.sql` on first boot, which takes a few more seconds. Three ways
to confirm, in increasing order of confidence:

**1. Container status**

```bash
docker compose ps
```

Both services should show `Up (healthy)`. If `portfolio-postgres` is missing entirely,
the images are still downloading — no containers exist until the pull completes.

**2. Init script output**

```bash
docker compose logs -f postgres
```

You are waiting for `database system is ready to accept connections`, preceded by a stream
of `CREATE TABLE`, `INSERT 0 …` lines and the row-count table printed at the end of
`seed-data.sql`.

**3. The verification script** — the authoritative answer

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1
```

```bash
bash scripts/verify.sh          # macOS / Linux / WSL / Git Bash
```

It checks container state, PostgreSQL readiness, that all 21 tables and the exclusion
constraint exist, that seed row counts match, that MongoDB responds to an authenticated ping
when it is running, and that the committed P4/P5 report, config and evidence files are
present. It does not require the P5 replication containers to be running; P5 has its own
lifecycle and the primary is intentionally stopped after the failover demonstration. Exit
code `0` means the P1–P4 environment is ready and the P4/P5 artefacts are present.

### If the Init Script Failed

A partially-initialised volume is worse than none: the entrypoint skips init whenever the
data directory is non-empty, so a failure leaves you with a half-built database that looks
healthy. Always rebuild the volume rather than retrying:

```bash
docker compose down -v
docker compose up -d
```

The `-v` is the important part — it deletes the volume.
